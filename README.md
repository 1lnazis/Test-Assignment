# Сервис котировок

Go-сервис с асинхронным обновлением валютных курсов. HTTP-ручка сохраняет запрос
в PostgreSQL и возвращает идентификатор, а фоновый воркер получает цену у Frankfurter.
API и воркер работают в одном процессе; очередь хранится в БД. Kafka не требуется.

## Запуск

Для запуска нужны Docker с Compose и доступ к интернету для загрузки образов,
Go-зависимостей при сборке и запросов к провайдеру. Локальная установка Go не нужна.
Приложение и PostgreSQL запускаются в отдельных контейнерах. API и воркер остаются
в одном Go-процессе внутри контейнера app.

Для постоянных локальных настроек можно один раз скопировать шаблон:

```bash
cp .env.example .env
```

Затем менять нужные значения в .env и запускать приложение обычной командой:

```bash
docker compose up --build
```

.env необязателен: без него используются значения по умолчанию из Compose.

Сначала Compose дожидается готовности БД по healthcheck, затем запускает приложение.
Миграции применяются приложением автоматически. Повторный запуск пропускает уже
применённые файлы. Таблица `schema_migrations` хранит их имена.

API доступен на `http://localhost:8080`. Порт PostgreSQL на хост не публикуется:
приложение подключается к `db:5432` по внутренней сети Compose. EXPOSE в образе
не означает публикацию порта на хост.

Запуск в фоне и просмотр логов:

```bash
docker compose up -d --build --wait
docker compose logs -f app
```

Остановка: Ctrl+C при запуске в терминале либо `docker compose down`.
Данные БД сохраняются в volume pgdata; обычный down их не удаляет.

Если порт 8080 занят:

```bash
APP_PORT=8081 docker compose up --build
```

Порт приложения внутри контейнера остаётся 8080, на хосте в этом примере используется 8081.
Можно использовать make: `make up` — фоновый запуск, `make run` — запуск с логами,
`make down` — остановка. Оба способа запускают один и тот же Compose-стек.

Посмотреть данные без публикации порта БД:

```bash
docker compose exec db psql -U quotes -d quotes
```

Для разработки можно запустить Go-приложение локально с отдельно доступной PostgreSQL
(потребуется Go версии из go.mod, сейчас 1.26.5):

```bash
DATABASE_URL='postgres://user:password@localhost:5432/quotes?sslmode=disable' go run ./cmd/app
```

Приложение не создаёт саму базу и роль пользователя; они должны существовать.
Адрес localhost:5433 из прежнего варианта Compose больше не работает: порт закрыт.

## API

Валютная пара `EUR/MXN` означает цену одной EUR в MXN. Список допустимых кодов
задаётся конфигурацией. Наличие кода в списке не гарантирует поддержку пары источником.

Создать запрос обновления:

```bash
curl -i -X POST http://localhost:8080/api/v1/quotes/updates \
  -H 'Content-Type: application/json' \
  -d '{"pair":"EUR/MXN"}'
```

Ответ: `202 Accepted`, `{"id":"..."}`. Заголовок `Location` содержит путь для чтения.
Принятие запроса не означает успешное получение цены. POST ждёт записи в БД,
но не обращения к провайдеру. Каждый POST создаёт новую джобу.

Получить состояние запроса, подставив его UUID:

```bash
curl -i http://localhost:8080/api/v1/quotes/updates/UUID
```

- `pending` — ожидает первой или повторной попытки;
- `processing` — захвачен воркером;
- `done` — цена получена; есть `price`, `provider`, `updated_at`;
- `failed` — окончательная ошибка в поле `error`.

Для найденного запроса ручка возвращает `200` во всех этих состояниях.
Клиенту рекомендуется проверять результат не чаще раза в секунду. Это договорённость
контракта: сервер не ограничивает частоту запросов и не гарантирует готовность через секунду.

Последняя **успешно сохранённая** котировка по паре:

```bash
curl -i 'http://localhost:8080/api/v1/quotes/latest?pair=EUR%2FMXN'
```

Ответ `200`, например:

```json
{"pair":"EUR/MXN","price":"21.072","provider":"frankfurter","updated_at":"2026-11-03T10:00:00Z"}
```

Цена передаётся строкой, в БД — `numeric(24,10)`, в Go — `decimal.Decimal`.
Перед записью выполняется округление до 10 знаков после запятой и проверка диапазона.
`updated_at` — время сохранения результата по часам БД, а не дата курса у провайдера.
Источник может вернуть тот же курс при нескольких обновлениях.

Если успешного обновления ещё не было, latest возвращает `404` и сам не создаёт джобу.
Ошибка нового обновления не удаляет предыдущую успешную котировку. Последняя выбирается
по времени успешного сохранения, а не по времени создания запроса.

Некорректный UUID/пара дают `400`; корректный, но неизвестный UUID — `404`;
ошибка обращения нашего API к БД — `500`. Ошибки предусмотренных ручек имеют JSON-формат
`{"error":{"code":"...","message":"..."}}`.

Для неизвестных путей и неподдерживаемых методов используются стандартные ответы
Go ServeMux: 404/405 с текстовым телом. У 405 есть заголовок Allow. Это поведение
маршрутизатора; отдельные бизнес-ручки для этих ошибок не добавлялись.

## OpenAPI

Контракт API описан в [openapi.yaml](openapi.yaml), формат OpenAPI 3.0.3.
В файле указаны все три ручки, параметры, схемы и примеры запросов/ответов,
статусы джобы, Location и ошибки. Порт локального API задаётся переменной port в servers;
по умолчанию 8080.

Для просмотра можно импортировать файл в [Swagger Editor](https://editor.swagger.io/).
Встроенной страницы Swagger UI в приложении нет. Спецификация поддерживается вручную:
при изменении API её нужно обновлять. Валидация запросов по-прежнему выполняется Go-кодом.

## Фоновая обработка

1. Воркер атомарно захватывает доступную джобу через один SQL-запрос с
   `FOR UPDATE SKIP LOCKED`, переводит в `processing`, увеличивает `attempts` и выдаёт аренду.
2. После завершения SQL обращается к провайдеру. Транзакция во время HTTP не удерживается.
3. Успех сохраняется через `Complete`. Временная ошибка планирует `Retry`,
   постоянная ошибка или исчерпание бюджета — `Fail`.
4. Запись исхода проверяет `id`, `status='processing'` и номер попытки.
   Поздний результат старой попытки не перезапишет более новую попытку.

Повторяем HTTP 408/429/5xx, сетевые ошибки, таймауты и оборванное чтение ответа.
Остальные HTTP-статусы, неправильный ответ и цена вне диапазона завершают запрос ошибкой.
По умолчанию три попытки **всего**, задержки между ними — 1 и 2 секунды.
При увеличении бюджета задержка растёт экспоненциально до 30 секунд.
Абсолютное время следующей попытки вычисляет БД, воркер передаёт только интервал.

Если процесс упал, `processing` с истёкшей арендой снова доступен для захвата.
Исчерпавшие попытки джобы переводятся в `failed` тем же SQL захвата, пачками до 100.
Уже работающая последняя попытка не завершается досрочно до истечения аренды.
При непустой очереди воркер берёт следующую джобу сразу; при пустой — ждёт интервал опроса.

Отмена приложения не превращается в ошибку провайдера: незавершённая джоба остаётся
под арендой. Уже полученный успешный ответ сохраняется с отдельным коротким контекстом.
Паника на обработке одной джобы логируется, цикл продолжается; джоба восстановится
после аренды. Ошибка захвата логируется с повторным опросом; ошибка записи исхода
останавливает приложение, чтобы не скрыть невозможность сохранить результат.

Семантика обработки допускает повторный вызов провайдера после сбоя — это не exactly-once.
Истёкшая аренда сама по себе не отменяет старый HTTP-вызов. Защита номера попытки
предотвращает устаревшую запись после перезахвата. Случайного разброса задержек (jitter)
и учёта заголовка `Retry-After` пока нет.

## Настройки

Go-приложение читает переменные окружения при запуске и само не загружает `.env`.
Compose может использовать `.env` для подстановки значений из docker-compose.yml.
Для длительностей используется формат Go: `500ms`, `5s`, `1m`.

Шаблон .env.example хранится в репозитории; .env содержит локальные значения и уже
исключён через .gitignore. Файл не копируется в образ: Docker получает значения
при запуске контейнера через environment в Compose.

Для подстановок вида `${WORKER_COUNT:-1}` приоритет такой:

1. Значение в окружении терминала, из которого вызван Compose.
2. Значение из .env в корне проекта при обычном запуске из этого каталога.
3. Дефолт после `:-` в Compose, если значение не задано или пустое.

Например, при WORKER_COUNT=2 в .env команда ниже запустит пять обработчиков,
не меняя файл:

```bash
WORKER_COUNT=5 docker compose up --build
```

Следующий обычный запуск без этого разового значения снова использует .env,
если переменная не экспортирована в терминале. Изменения окружения применяются
при запуске/пересоздании контейнера; работающее приложение не перечитывает .env.
Посмотреть итоговую конфигурацию можно командой `docker compose config`.

В шаблоне перечислены настраиваемые подстановки Compose. Адрес БД в DATABASE_URL
(db:5432) и внутренний HTTP_ADDR=:8080 в текущем Compose заданы явно, поэтому одноимённые
строки в .env их не заменяют. Внешний HTTP-порт меняется через APP_PORT.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATABASE_URL` | обязательна; Compose задаёт адрес db:5432 | PostgreSQL |
| `HTTP_ADDR` | `:8080` | Адрес API |
| `CURRENCIES` | `USD,EUR,MXN,RUB,KZT` | Допустимые коды |
| `LOG_LEVEL` | `info` | Уровень JSON-логов |
| `WORKER_COUNT` | `1` | Параллельные обработчики |
| `MAX_ATTEMPTS` | `3` | Максимум захватов джобы |
| `POLL_INTERVAL` | `1s` | Пауза при отсутствии работы/ошибке захвата |
| `RETRY_BASE_DELAY` | `1s` | Первая пауза перед повтором |
| `RETRY_MAX_DELAY` | `30s` | Верхняя граница паузы |
| `QUOTE_TIMEOUT` | `5s` | Таймаут одного обращения к источнику |
| `DB_TIMEOUT` | `3s` | Таймаут операции очереди у воркера |
| `LEASE_DURATION` | `30s` | Аренда захваченной джобы |
| `SHUTDOWN_TIMEOUT` | `10s` | Общий бюджет штатной остановки |

Настройки воркера, валют и логов передаются через environment в Compose. Например:

```bash
WORKER_COUNT=5 docker compose up --build
```

APP_PORT относится к публикации HTTP-порта на хост. STOP_GRACE_PERIOD задаёт время,
которое Docker даёт контейнеру до принудительного завершения; по умолчанию 20 с.
При изменении SHUTDOWN_TIMEOUT нужно согласовать и STOP_GRACE_PERIOD, оставив запас.

Аренда должна быть больше `QUOTE_TIMEOUT + 2 * DB_TIMEOUT`, чтобы покрыть захват,
получение и сохранение с запасом. Бюджет остановки должен превышать `DB_TIMEOUT`.
Параметры проверяются до подключения к БД. URL Frankfurter передаётся из `main`
через константу клиента; конструктор принимает URL также для тестирования.

При Ctrl+C/SIGTERM отменяем воркер, прекращаем приём новых HTTP-запросов,
ожидаем текущие запросы и воркер, затем закрываем пул БД. По истечении бюджета
HTTP-соединения закрываются принудительно. Go не позволяет принудительно завершить
горутину: зависимости воркера обязаны учитывать контекст. Если такая зависимость
нарушит контракт, ожидание воркера может превысить бюджет; пул до его завершения не закрывается.

## Структура

| Каталог | Ответственность |
|---|---|
| `cmd/app` | Сборка зависимостей, запуск и остановка |
| `internal/config` | Чтение и проверка окружения |
| `internal/domain` | Валюты, пары, состояния и доменные ошибки |
| `internal/httpapi` | Маршруты, JSON, HTTP-ошибки и middleware |
| `internal/service` | Проверки входных данных и вызовы репозитория |
| `internal/storage/postgres` | SQL, пул, миграции и реализация очереди |
| `internal/provider/frankfurter` | Один HTTP-запрос к Frankfurter v2 |
| `internal/worker` | Интерфейсы зависимостей, цикл, ретраи, таймауты |

## Проверки

Полный набор с настоящей БД и race detector, без локального Go и без открытия порта БД:

```bash
docker compose run --build --rm test
```

То же самое через Makefile: `make test-integration`. Сервис test относится к профилю
tools и не запускается обычным up. Он стартует только при явном обращении к нему,
использует build-stage с Go и C-компилятором для race detector и удаляется после тестов.
В образ app эти инструменты не входят.

Для локальной работы с установленным Go:

```bash
make test
make vet
```

`make test` запускает тесты с race detector; без TEST_DATABASE_URL проверки PostgreSQL
будут пропущены. При наличии отдельно доступной БД её URL можно передать вручную.
Интеграционные тесты создают отдельные случайные схемы и удаляют их после выполнения;
роль должна иметь соответствующие права. Используйте локальную тестовую БД.

Проверяются конкурентный захват без повторной выдачи при действующих арендах,
восстановление, защита старой попытки, округление, повторы, отмена и остановка.
Сквозные тесты соединяют HTTP-слой, настоящую PostgreSQL, воркер и локальный сервер,
подменяющий провайдера. В этих тестах ожидание ретраев убрано; расчёт задержек
и недоступность будущей джобы проверяются отдельно. Внешний API для тестов не нужен.

## Ограничения

Один внешний источник, один процесс приложения, нет авторизации, rate limit,
дедупликации одинаковых POST, удаления старых запросов и длительных нагрузочных испытаний.
Нагрузка и p99 для произвольного окружения не гарантируются. Несколько обработчиков поддерживаются
очередью, но тест конкурентного захвата не является замером производительности сервиса.
Брокер сообщений не используется. В обычном запуске работают два контейнера: app и db;
test — только одноразовый инструмент проверки.
